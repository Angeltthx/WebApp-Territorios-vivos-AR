# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A browser-based WebAR experience (image tracking, not markerless/world tracking) that works on iPhone Safari and Android Chrome with no app install. Uses **MindAR** for computer-vision tracking (WebXR is not an option — Safari on iPhone doesn't support it) and **Three.js** for rendering.

The marker is an illustrated map of Nuquí, Chocó (`public/targets/map.jpg`). **Seeing the map is not enough to see the animals** — it draws a **gold dashed outline that beats** around each of the four (whale, guan/pava, crab, turtle), traced from how that animal is *drawn*, and the 3D model only materializes, with a puff of smoke, once you bring the phone close to that one. Discovering it **unlocks it for the rest of the session** (walking away never hides it again) and opens its card — name, a scientific / common-name line, and every paragraph of text the team delivered for it — closed with an X. **While an animal is in focus, the focus is locked**: approaching another animal does nothing until the X. In focus it **sounds**: its habitat plays in a loop (sea, mangrove beach, reef, Chocó forest) and one of its real recorded calls plays on entry and another, different one every 10–16 s. **Once all four animals are found, a small pulsing marker appears on each of the map's printed texts**, and a message in the viewfinder style — «¿Quieres conocer más del Chocó? Toca los puntos del mapa para interactuar» — says so; it has no buttons, leaves after 15 s or as soon as a text is opened, and comes back after 35 s without opening anything. The markers sit on the tourism paragraphs, the directory of local businesses, the pink place labels, the town names, the harlequin frog label and the website. Tapping one opens it big for reading over the dimmed camera, no card behind it: the SAME text, transcribed, in the map's own styles, justified, with the drawing that goes with it cut out without its background (the Emberá huts, the dancers, the frogs) and the sound of the place it talks about. If no animal is found 7 s after the map is in frame, a line drawing loops under «Acerca tu cámara a un animal»: a phone with viewfinder corners descends toward a gold dashed outline on a dashed map, the animal grows on its screen and the outline beats — the app's own visual language, showing what to look for and what to do. **Tapping a revealed animal plays a tap sound** (a blow, a splash, a scuttle — different from its calls) and plays its gesture — the whale breaches and dives, the turtle leaps out and falls back in, the crab scuttles, the guan sings; tapping again mid-gesture does nothing until it finishes, and the animal never changes size; a dormant outline is deliberately not tappable.

Opening the link shows the **splash screen** (`#boot`) the company's designer delivered — one image carrying the title, the photo, the partner logos and a drawn **«Iniciar experiencia AR»** button — and it stays until that button is tapped; only then is the camera requested. That tap matters twice over: a system permission prompt over a page nobody asked for gets denied, and iOS only unlocks audio (and stops treating the camera feed as a player) inside a real user gesture. An earlier version started by itself after 4 s; the design brought the button back, and the button brought the gesture back with it. Three overlays carry the instructions in order: `#boot`, then `#guide` (viewfinder frame in the map's exact 1000:1432 proportion, "Apunta al mapa de Nuquí"), then `#approach` ("Acerca tu cámara a un animal"). The buttons left are **«?»** (top right), which brings the guide back for 5 s; **☰** (top left), a round translucent twin of it that drops down a semi-transparent menu — three options («Historia», «Redes sociales», «Próximamente»), wired to nothing yet; and **Reintentar**, which appears solely on error — without it, denying the camera by accident would kill the session until reload. «?» and ☰ share one visibility rule: they show once the session has started and hide while an animal's card is open. Dragging turns an animal in place; **there is no pinch-to-scale** — it was removed on request, because each animal's size is calibrated in the catalog and hand-scaling broke that hierarchy. The four icons are `.glb` models made by the team's 3D designer, in `public/models/`; the sounds are real recordings in `public/audio/`, built by `npm run build-audio` (see below); the old Web Audio synthesis (`sound` in the catalog) remains the fallback for an animal without recordings. `PrimitiveFactory` still builds a procedural stand-in for every animal — switch a catalog entry back to `ModelSource.primitive(...)` and it runs with no assets at all.

## Commands

```bash
npm install            # slow: pulls in MindAR + TensorFlow.js
npm run dev             # vite --host over HTTPS (required for camera off localhost)
VITE_HTTP=1 npm run dev # same, no TLS — desktop-only inspection (see /verify.html)
npm run build           # vite build
npm run preview         # vite preview --host
npm run typecheck       # tsc --noEmit
npm run prepare-target  # "Mapa para el fondo.jpeg" -> public/targets/map.jpg
npm run compile-target  # public/targets/map.jpg -> public/targets/map.mind
npm run optimize-models # models-src/*.glb -> public/models/*.glb (webp + draco)
npm run optimize-splash # "Pantalla Inicial.jpeg" -> public/splash/inicio.{webp,jpg}
npm run build-audio     # audio-src/{sources,clips}.json -> public/audio/<animal>/*.mp3 + CREDITOS.md
npm run cut-illustrations # map drawings without background -> public/illustrations/*.webp (add `-- preview`)
npm run bench-detection # measures how well a .mind survives glare (no camera)
npm test                # tests/regressions.test.ts, bundled by Vite and run with node:test
```

There is no lint script. `npm test` covers domain rules, the animator, the tap
choreographies and the pin/adapter wiring (no WebGL needed). For detection,
`npm run bench-detection` is the tool: it runs MindAR's real `Detector` + `Matcher` against synthetic
frames of the map under increasing glare and distance, and reports both hits and
**inlier counts**. Compare two `.mind` files with it before believing any claim
that detection got better — pass/fail alone flips on noise near the threshold,
the inlier total is the signal.

`npm run dev` prints a LAN address (`https://192.168.x.x:5173`); open that from the phone, not `localhost`. Safari will warn about the self-signed cert — accept via *Show Details → Visit this website*. Debugging requires the physical device: Safari Web Inspector (from a Mac) for iPhone, `chrome://inspect` for Android.

### Verifying without a phone

`/verify.html` (dev-only — `vite build` bundles `index.html` only) mounts **the real `MarkerPin` objects** onto a picture of the map, placed in the exact anchor plane and scale MindAR uses. It reveals all four after 2.5 s, so the first seconds show the dashed outlines and the rest shows the models; `?reveal=999999` freezes the outlines for measuring them, and a short value lets you catch the smoke. It checks shape, placement and colour, but **not** movement: a headless/background tab has `requestAnimationFrame` frozen (`document.visibilityState === 'hidden'`), so every screenshot of it comes out identical and the beat has to be judged on a real screen. The orthographic view has no perspective to hide a mistake: if an outline doesn't sit on its animal, the catalog coordinates are wrong. Run `VITE_HTTP=1 npm run dev` and open it — the self-signed cert otherwise blocks headless/automated inspection. Clicking an animal in the flat view plays its tap gesture. Because rAF freezes in a background tab, the page exposes three console helpers for inspecting motion anyway: `tap('whale')` starts a gesture, `stepVerify(1.9)` advances every pin by exactly that many seconds and renders — so a screenshot catches the whale mid-jump or the splash on the frame it fires — and `measureIcons()` returns each animal's on-screen width in map widths (take a screenshot first so the reveal has actually rendered).

`node scripts/preview-spots.mjs '[{"u":0.26,"v":0.22}]' out.jpg` draws crosshairs on the map at given normalized coordinates — use it to measure a new `spot` before putting it in the catalog.

`node scripts/trace-outline.mjs whale ascii` traces an animal **as it is drawn on the map** and prints it as an ASCII picture; `… whale poly 22` prints the same thing as the `outlineShape` block the catalog expects. **Always look at `ascii` first**: the trace is a per-animal colour rule plus the largest matching blob, so if the rule leaks into the background the outline comes out enormous and the ASCII shows it instantly.

## Architecture

Hexagonal (ports and adapters). The single rule: **dependencies point inward.** Read `README.md` for the full rationale (in Spanish) — the essentials:

```
src/
├── domain/            Pure rules, zero external imports.
│   ├── entities/       ArModel, ArSession, Placement
│   └── value-objects/  ModelId, Scale, Vector3, MarkerSpot, ModelSource, SoundProfile, Stabilization, IconPose, Proximity, Discovery, AnimationSequence, Soundscape, MapText
├── application/
│   ├── ports/          TrackingPort, ScenePort, AudioPort, InteractionPort, ModelRepository, AnalyticsPort
│   └── use-cases/       StartArExperience, TransformPlacement, PlayModelSound, DiscoverNearbyModel, CloseFocus, AnimalSoundscape, OpenMapText, RecurringNudge (ui)
├── infrastructure/     MindAR and Three.js live ONLY here.
│   ├── mindar/          MindArRuntime (shared instance, owns the render loop) + FrameLockedBackground
│   ├── tracking/        MindArTrackingAdapter
│   ├── rendering/       ThreeSceneAdapter, MarkerPin, IconLoader, IconAnimator, TapChoreography, WaterSplash, MapTextHotspot, IconSilhouette, SmokePuff, PrimitiveFactory
│   ├── interaction/      PointerInteractionAdapter (raycast + gestures)
│   ├── audio/            WebAudioAdapter (recordings: clips + seamless ambience loop; synthesis fallback)
│   ├── repositories/    StaticModelRepository + NUQUI_CATALOG, StaticMapTextRepository + NUQUI_MAP_TEXTS
│   └── di/container.ts ← composition root
├── ui/                 ArView — paints state, emits intents; knows nothing about MindAR/Three.js
└── verify.ts           Dev-only coordinate check (see above)
```

- **`TrackingPort` is the port that justifies the whole architecture.** MindAR (unmaintained since Jan 2024, single maintainer) is the volatile piece. Swapping it for WebXR/Zappar/8th Wall means writing a new adapter and changing exactly two lines in `src/infrastructure/di/container.ts` (marked with arrows in the file) — domain, use cases, and UI stay untouched.
- `container.ts` is the **composition root**: the only place concrete implementations get wired to ports. Start here to see how everything connects.
- The 60fps render loop is deliberately **not** behind a port (abstracting per-frame matrices was judged not worth the cost); it lives in `MindArRuntime`, and adapters subscribe via `onFrame()`.
- **Proximity reveal spans all three layers, and that split is the point.** `Proximity` (domain) owns the rule — two distances plus an aim radius, with **hysteresis**: a single threshold makes an animal flicker several times a second when you hover at the boundary. `ThreeSceneAdapter.evaluateProximity` owns the measurement, because only it has the matrices, and it runs in the render loop rather than behind a port for the same reason the loop itself isn't behind one. It picks the pin **nearest the screen centre** (on a flat map all four sit at similar distances, so aim is what says *which* animal) and reveals it if it's also close enough. `DiscoverNearbyModel` (application) decides what approaching *means* — unlock the animal and put it in focus — and records it in `ArSession`.
- **Unlocked and focused are two different things, and `Discovery` (domain) keeps them apart.** Unlocked is forever: an animal you got close to stays on the map for the rest of the session even if you walk away, which is what makes exploring the map *advance* instead of repeat. Focused is momentary: the one being shown big with its card, closed by the X (`CloseFocus`) — and closing it hides nothing. Walking away from an animal is not an instruction, so it closes nothing either.
- **`MarkerSpot` (domain) + `MarkerPin` (infrastructure) are the pairing this design rests on.** `MarkerSpot` says *"the crab is at (0.487, 0.472) of the image"* — normalized 0–1 from the image's **top-left**, the way you'd measure on the image file. `MarkerPin` translates that into MindAR anchor coordinates and builds the outline, tap zone, smoke and floating icon. `MarkerPin` deliberately **does not depend on MindAR or the runtime**, which is exactly what lets `verify.html` mount the real pins without a camera.
- **Anchor coordinate system** — verified in MindAR's source, not guessed (`image-target/three.js:214-229` and the comment on `controller.js:_glModelViewMatrix`):
  - Origin is the **center** of the marker image; the image **width is 1 unit**, its height is `targetAspect`.
  - **+X** right, **+Y up** (MindAR flips the image's Y with `y' = h - y`), **+Z out of the paper toward the camera**.
  - The conversion lives in one function, `anchorPositionOf`: `x = u - 0.5`, `y = (0.5 - v) * targetAspect`.
- Scene graph hierarchy (needed to follow `ThreeSceneAdapter`):
  ```
  scene → follower (marker pose, SMOOTHED — content never hangs directly off MindAR's anchor)
            └── overlay (global offset)
                  └── MarkerPin ×4 (fixed position = its MarkerSpot)
                        ├── outline (dashed silhouette flat on the paper,
                        │     shown while the animal is still dormant)
                        ├── tap zone (invisible, generous)
                        ├── smoke (SmokePuff — sprites, fires once on reveal)
                        └── lift (floats along +Z, bobbing; height adapts
                              so a deep icon never sinks under the paper)
                              └── icon (spun and scaled in place)
  ```
  Content is deliberately not parented directly to MindAR's anchor because doing so inherits its raw frame-to-frame tracking jitter. `follower` copies the anchor pose every frame through `PoseFilter`, a **One Euro filter**: the cutoff rises with the *filtered* speed of the map (`Stabilization.restCutoffHz` + `linearResponse`·map widths/s + `angularResponse`·rad/s, one cutoff shared by position, rotation and scale so the animals never slide over the paper). A tremor goes back and forth, its filtered speed stays near zero, and the animals stay still; a sweep of the phone keeps its direction and opens the filter with no visible lag. It replaced a per-frame snap threshold (smooth below `SNAP_DISTANCE`/`SNAP_ANGLE` per frame, follow outright above), which let the vibration through on noisy phones and shaky hands — a single bad frame crossed the threshold — so the animals "vibrated depending on the device". `npm test` checks a 5 Hz tremor is cut to under 30% and a 1 map-width/s sweep lags under 0.06. The base level is fixed at `Stabilization.default()` — the Fast/Balanced/Stable button was removed from the UI, but `StartArExperience.applyStabilization` is still there if a control is ever wanted back.
- **Rotation and scale never move an icon off its animal.** `Placement.rotationY`/`scale` spin and resize each icon *in place*; a change that makes them displace the icons is a bug, not a feature. `Placement.offset` moves the whole overlay and is currently always zero.
- `ArSession` (in `domain/entities/ArSession.ts`) is a frozen state machine (`idle → preparing → searching → tracking/lost → error`) with guarded transitions — invalid states (e.g. `tracking()` without a prior `Placement`) throw. `TransformPlacement`/etc. read/write this via the use cases, never by mutating fields directly.
- Path aliases (`@domain`, `@application`, `@infrastructure`, `@ui`) are defined in both `tsconfig.json` and `vite.config.ts` — keep them in sync if either changes.

## Project-specific gotchas (read before touching related code)

- **The proximity thresholds in `Proximity.default()` are placeholders until someone calibrates them with the printed map.** They cannot be derived at a desk: they depend on the real camera's field of view and on how big the map is printed. `ThreeSceneAdapter` logs `[Proximity] <animal> distancia=… desvío=…` once a second for exactly this — read it on the phone and set the numbers from what you see. That log is not debug leftover; deleting it removes the only way to tune this.
- **Getting close enough to reveal an animal can be close enough to lose the marker.** MindAR needs a decent chunk of the target in frame; if `revealDistance` is set so tight that only one animal fills the screen, tracking drops and everything vanishes. That tension is inherent to the interaction, and calibration means finding the window where both hold.
- **The outline is gold and beats, and both were forced by the phone.** It started white (the same visual grammar as the "Apunta al mapa" viewfinder) with a 2% sine breath, and on the map nobody noticed it: the illustration is already full of white — the place names, the species labels, the surf, the clouds — so one more white line reads as part of the drawing, and a slow continuous movement is exactly the one the eye stops seeing after two seconds. Now: `OUTLINE_COLOUR` 0xffc53d, a colour the map does not contain, over the dark backgrounds all four animals sit on (turquoise sea for three, green jungle for the guan); thickness up from 0.004 to 0.0065 map widths; and a **heartbeat** instead of a breath — grows 11% and brightens over 0.31 s, returns by 0.62 s, then rests until the 2.4 s cycle comes round. The silence is what makes the next beat register. Each pin keeps its `phase`, so the four never beat in unison: synchronised they look like a screen effect, staggered they look alive. The guide viewfinder stays white on purpose — white frames the map, gold says there is something here to find.
- **The dashed outlines are traced from the DRAWING, not deduced from the `.glb`** — all four carry an `outlineShape` in the catalog, measured on `map.jpg` with `scripts/trace-outline.mjs` and in the same normalized coordinates as `spot`. `IconSilhouette` (which flattens the model, rasterizes its triangles and walks the boundary) is the fallback for an animal nobody has traced yet, and `outlineView`/`outlineSpin`/`outlineMirror` are its per-animal tuning. It is a fallback because the illustrator's pose and the model's pose are not the same pose: the whale on the map dives with its tail up, the turtle swims diagonally with its flippers spread, and no rigid projection of the model gives that — checked in `/verify.html`, where the deduced silhouettes sat off their animals while the traced ones land on the drawing. Change the map and these have to be re-traced, exactly like the `spot`s.
- **`Box3.setFromObject` returns a WORLD-space box, and a `MarkerPin`'s group is already translated to its animal.** Measuring the icon without subtracting `group.position` folds the distance from the map's centre into the "width": the guan, out at the right edge, measured nearly four times wider than it is, while the crab — which sits almost dead centre — looked correct and hid the bug. `measureIconExtents` subtracts it explicitly. The group has no parent and no rotation at construction time, which is what makes that subtraction exact.
- **The splash's start button is the only user gesture in the whole experience, and three separate things depend on it**: iOS granting the camera, iOS unlocking the `AudioContext` (`StartArExperience.execute` calls `unlock()` as its first statement, inside the click), and Safari not treating the camera feed as a player to put controls on. The `pointerdown` listener in `src/main.ts` still unlocks audio too — belt as well as braces, and cover if the button ever goes away again. If any of the three ever breaks, check first whether something moved the camera start off that click.
- **The splash is one flat image with the UI drawn into it: it fills the screen, its crop is capped, and the real button is a transparent hotspot on top.** `#boot-art` is a frame with the image's exact proportion (`--splash-ar`), sized by a single expression — cover the viewport, but never grow past `--vh * 1.42`. **That cap is derived from the art, not chosen.** The only untouchable band runs from the title (starts at 20.5% of the file) to the foot of the partner logos (TIC, Ministerio de Culturas, CO·CREA, ending at 89.8%) — cutting those logos is a funding problem, not a taste one. So 20.5% is expendable above and 10.2% below, the crop is split in that same 67/33 proportion (`bottom: calc((--art-h - --vh) * -0.33)`), and 1.42 is exactly the frame height whose crop lands inside both budgets (19.8% off the top, 9.8% off the bottom). Change the photo and those three numbers get re-measured together.
- **A cap of 1.22 with an 80/20 split was the first attempt, and it letterboxed real phones.** Anything past the cap narrows the frame and shows blurred side margins, and 1.22 put that threshold at a viewport ratio of 0.549 — with a comment claiming no phone in portrait reaches it. Phones do: the height that counts is the *visible* one, and a small iPhone with both Safari bars showing is about 375×560, a ratio of 0.67. It came back as "the cover looks cut, I see the edges" from the one device that matters. The 67/33 split is what buys the bigger cap: a fixed 80/20 split cannot go past 1.32 without eating the title.
- **The last two or three pixels of margin are closed by stretching, and the stretch decays to nothing.** Even at 1.42 the squarest phones leave a hairline band, and a hairline of blur reads as a bug while 4% of horizontal stretch on a photo of mangrove reads as nothing (the button is positioned in percentages of the frame, so it stretches with it and still lands on the drawn button). `--hueco` is the missing width and the rule adds `max(0px, min(--hueco, 4% of the frame, 12% of the frame − --hueco))`: it fills a small gap exactly, caps at 4%, and closes back to zero as the gap grows — so a tablet, where the whole photo with margins is the *right* look, gets no distortion at all. It is continuous, so no screen size makes the splash jump.
- **That sizing deliberately avoids a `min-aspect-ratio` media query, which is what broke it the first time.** The aspect a media query sees in iPhone Safari counts the address bar, so a phone held upright reported ~0.53 and tripped a threshold meant for tablets: the splash snapped to letterboxed with side margins on the exact device it was designed for. Viewport ratios on a phone are not what they look like on paper — express this kind of rule as a continuous `min()`/`max()` on lengths, not as a breakpoint. Check a change to it by measuring, not by eye: mount the page in an iframe sized 375×560, 390×744 and 768×1024 and read `#boot-art`'s rect against the title and logo percentages.
- **The start button is drawn into the photo, so its interactivity is added on top.** `#start` is transparent and placed in percentages of that frame (measured on the file: 32.6%–69.2% across, 66.3%–72.0% down), so it lands on the drawn button at any size. Since a photo cannot react, a slow `start-halo` ring says "tap me" and `:active` adds the press. Heights use `--vh` (`100svh` where supported). Replace the art with `npm run optimize-splash`, which prints the new `--splash-ar`; if the button moves in the design, re-measure those percentages.
- **The camera `<video>` must be muted BEFORE MindAR gets the stream, not after.** MindAR creates the element and then sets `muted` as an *attribute* (`three.js:92-96`), which only feeds `defaultMuted` — and `defaultMuted` decides the muted state at element *creation*. Set afterwards, it leaves the `muted` property `false`, so the camera plays as an unmuted, large, self-starting video: exactly the case iOS Safari attaches its media controls to, which is where the **pause button in the middle of the screen** came from. CSS cannot mop it up — modern iOS controls ignore `::-webkit-media-controls-*`. `MindArTrackingAdapter.start` therefore calls `silenceVideoChrome` *without awaiting* `mindar.start()`: MindAR appends the video synchronously on entering `_startVideo` and only then asks for the camera, and that asynchronous gap — permission, hardware — is the one moment the element exists and is not yet playing. Silencing it after `start()` resolves is too late: Safari has already attached the controls and does not let go.
- **`WebAudioAdapter.unlock()` must be called synchronously inside the Start button's click handler** (see `StartArExperience.execute`, where it is the first statement in the `try`, before any `await`). iOS Safari keeps the `AudioContext` suspended forever if unlock happens outside a real user gesture. Don't move audio unlocking behind an `await` chain or into a different handler — what matters is where the call *starts*, not where its promise is awaited.
- **Animal sounds are real recordings with open licences, and the pipeline is what keeps it that way.** `audio-src/sources.json` lists every source with its URL, author and licence; `audio-src/clips.json` says which slice of each one every animal uses (≤ 5 calls, taps, one ambience — possibly a mix of layers). `npm run build-audio` downloads the originals into `audio-src/.cache/` (git-ignored: the waves alone are 17 MB), cuts, makes mono, normalizes loudness (−16 LUFS calls/taps, −24 ambience) and encodes MP3 — 29 files, 1.6 MB — and writes `public/audio/CREDITOS.md`, because the guan recordings are CC BY-SA and require attribution. Like models, `public/audio/` is committed (Netlify only runs `npm run build`). `ffmpeg` comes from `@ffmpeg-installer/ffmpeg`, which ships the binary without an install script, so it works with `ignore-scripts`. Its ffmpeg is from 2018: `amix` has no `normalize` option. **Every candidate's page was read before using it**, and several were dropped: a crab "recording" that was a street market, a "whale song" that is a slowed-down human voice, a "whale blow" that is sound design, a mangrove with city traffic. Honest limits, also noted in the catalog and the credits: there is **no open recording of *Penelope ortoni*** (xeno-canto sits behind a bot wall and its API needs a user key), so the guan uses same-genus *Penelope* guans from the Colombian/Ecuadorian Andes; **crabs and sea turtles barely vocalize**, so they use characteristic sounds (steps — one of them foley —, underwater bubbles, a partly synthesized submerge). If the team gets real recordings, add them to `sources.json`/`clips.json` and re-run — nothing else changes.
- **The map's texts are a reward, and they are TRANSCRIBED, not cropped.** `NUQUI_MAP_TEXTS` holds every readable text on the map word for word — including the map's own inconsistencies («Las Serranía» on the pink label vs «Las Serranías» in the directory, «COQUI» without accent, «ecoturistica» without accent): what is shown is the map, not a correction of it. Cropping and enlarging the image was ruled out because the whole map is only 1000 px wide; enlarged small print is mush. Each entry has an `area` measured in pixels on `map.jpg` and checked by drawing the rectangles over it (same coordinates as `spot`), `blocks` that say HOW it is printed (`paragraph`, `directory`, `pin`, `place`, `sea`, `species`, `link`), a `backdrop` (`sea`/`forest`: the map colour it sits on) and an `ambience`. Change the map and these are re-measured and re-transcribed, like the spots and outlines. `npm test` checks the areas never overlap and every ambience file exists.
- **Map-text markers: all animals found and nothing open.** `Discovery.hasFoundAll(total)` turns them on; `Discovery.reading` is a third state next to unlocked/focused, and `isBusy` (an animal OR a text open) is the single lock: a text cannot open over an animal, an animal cannot open over a text, and the X (or a tap outside) closes whichever is open, then `resume` lets a nearby animal in. There was an intermediate version where the markers waited for the user to accept a button-card («Toca para interactuar» / «Ahora no»); it was dropped as a pointless step, and the card's filled dark style clashed with the rest of the UI. Now the markers appear on their own and the message only tells; it copies the guide viewfinder (dashed white border, viewfinder corners, Fraunces with shadow) and its show/hide/come-back cycle lives in `RecurringNudge`, tested with a fake clock — do not verify it in a background tab: Chrome delays chained timers there by up to a minute. **The markers were gold sparkles first, and on the phone they read as decoration**, not as something to tap; `MapTextHotspot` now draws the universal "something here" of a digital map — a small dot with two out-of-phase expanding translucent rings, each marker with its own phase — plus an invisible tap plane that is the text itself (0.004 of margin). `PointerInteractionAdapter` tells animals (`userData.modelId`) from texts (`userData.textId`). **The reading view has no coloured card**: it was a turquoise/green panel and hid the map; now the text floats over the dimmed camera with a text-shadow, paragraphs justified with Spanish hyphenation. **Illustrations** (`MapText.illustration`) are cut from `map.jpg` by `npm run cut-illustrations`: flood-fill the jungle-green background from the crop border with a per-drawing colour rule, keep big blobs, fill enclosed holes, feather 1 px, ×2 lanczos, WebP with alpha (68 KB for three). The frogs invert the rule (frog = red or black-with-no-green), because leaves, flowers and the blue species label surround them. As with outlines: look at `-- preview` (written to the git-ignored `.preview/`) before trusting a cut. The reading fonts (Merriweather, Arvo, Oswald) load only when the texts unlock. There is no open recording of marimba de chonta/currulao, so the dance and directory texts sound like the coast; the harlequin frog uses *Oophaga pumilio* (same genus, CC BY 3.0). `verify-ui.html` has «Texto» (`?text=<id>`), «Invitación» and «Acercarse» (wait 7 s for the approach hint) at six screen sizes; `/verify.html` shows the markers over the map.
- **Tap zones are the animal's own footprint, not a fixed disc.** `MarkerPin` used a 0.12-map-width disc for every animal — bigger than the crab — and with the text planes padded by 0.02 on top, tapping a marker near an animal hit the animal. Now the disc is an ellipse scaled every frame to the icon's measured half-width/half-height × its applied scale × `TAP_FOOTPRINT_MARGIN` (1.05); the model's meshes are raycastable too, so the disc only covers its base. `npm test` checks it stays under the old size and follows the animal's shape. **That was not enough, because three's `Raycaster` does not skip invisible objects**: the smoke sprites (grown to ~0.16 map widths after the reveal), the water splash and the faded outline were still invisible tap zones around every animal. `MarkerPin` now nulls `raycast` on all of those, `PointerInteractionAdapter` ignores any hit that is not visible up its whole parent chain, and the footprint disc (`userData.tapZone`) *yields to a text*: the animal floats above the paper, so its disc is always nearer the camera than a text beside it. The animal's actual body still wins over a text. **Removing those phantom zones exposed a second bug they had been hiding: three caches a `SkinnedMesh`'s bounding sphere/box the first time it raycasts, in whatever pose the clip had then, and uses it as a pre-filter forever.** The first tap computed it for all four at once; after that the animals moved on with their clips, their bodies left the stale box, and tapping another animal did nothing. `PointerInteractionAdapter` recomputes both for every skinned mesh before each tap (only on pointer-up, so the vertex walk costs nothing per frame); `npm test` moves a skinned body after a first tap and checks it is still hit.
- **The approach hint is a timer in `ArView`, on purpose not in the domain.** It is pure presentation: 7 s (`STUCK_HINT_MS`; 12 felt too long) of `needsApproachHint` without finding any animal. The clock keeps running if the hint is briefly covered (menu, «?») and stops for good at the first discovery. It shows the gesture that actually works — bringing the phone closer — not a pinch: there is no pinch-zoom in this app. A first version drew a hand holding the phone; it did not match the UI and was replaced by the phone-over-gold-outline drawing.
- **In focus, the focus is locked (`DiscoverNearbyModel`).** With the whale open, sweeping the camera over the crab used to swap animals mid-card and break the experience. Now a nearby animal is ignored while another is focused, but *remembered*: when the X closes the card, `CloseFocus` calls `resume`, and if the camera is already next to a DIFFERENT animal, that one is discovered at once (no need to walk away and back). The one just closed never reopens by itself.
- **`AnimalSoundscape` decides what sounds and when; `WebAudioAdapter` only plays.** On focus: ambience + a call after 400 ms + another different call every 10–16 s (`pickDifferent`: never the same recording twice in a row); on tap: a tap sound; on close: fade out. A scheduled call re-checks the session before playing, so a card closed any other way (session stopped) goes quiet too. The ambience is not `loop = true` — field-recording slices leave an audible seam — but overlapping layers with equal-power (sin/cos) crossfades; linear fades dipped ~3 dB at each joint. Recordings are preloaded one at a time after the models (`soundPreloadOrder`: every ambience and first call before any tap), and a clip that arrives more than 1.5 s late is dropped rather than played out of context.
- **Envelope floors, not `durationMs`, decide how long a sound is actually heard.** An exponential ramp down to ~0 crosses four decades: half way through it is already at ~1% of the peak, so a 220 ms profile was audible for about 20 ms and taps felt mute. The bus decays to 4% of peak (−28 dB) and the overtone gains to 10% of their weight — the two envelopes multiply, so both have to stay off zero. Verified by rendering the real adapter through an `OfflineAudioContext` and measuring: audible time roughly tripled (whale 231 → 726 ms, crab 23 → 75 ms) with peaks near 0.5 and no clipping.
- **`three` is pinned to `0.160.0`** — the version MindAR's docs were verified against. Do not bump it without testing on a real device; MindAR has never been tested against newer Three.js releases.
- **`src/types/mindar.d.ts` is hand-written**, not official types — names were verified against the actual `mind-ar@1.2.5` bundle, not against a spec.
- `.npmrc` sets `ignore-scripts=true`, so install-time scripts (postinstall, etc.) are skipped for all dependencies. **This is why the target compiler is hand-rolled:** MindAR's own `OfflineCompiler` imports the native `canvas` package, which never gets built here. `scripts/compile-target.mjs` subclasses `CompilerBase` (which has no canvas dependency) and feeds it a jpeg-js-decoded buffer through a two-method canvas shim. Don't "fix" it by adding `canvas` — it needs a native toolchain on Windows.
- **Models are a two-folder pipeline: `models-src/` (the designer's originals, not served) → `npm run optimize-models` → `public/models/` (what ships).** Never optimize in place: texture compression is lossy, so re-running over its own output degrades quality a little each time. The delivered originals were 8.4 MB and 96–99 % of that was **textures**, not geometry — so the thing that cuts weight is WebP re-encoding, not Draco (which three of the four already had). The script does both anyway and lands at 3.2 MB. Both folders are committed: Netlify runs `npm run build` only, so `public/models/` must already hold the optimized files.
- **All four animals use `view: 'front'`** — upright on the map, facing whoever holds the phone (the user's explicit call: every animal looks at the user); the drag gesture turns them sideways. The whale spent one iteration in `'side'` because "the whale looks too big" was blamed on the map; the real culprit was the **focused close-up** (see `STAGE_MAX_WIDTH` below). Facing forward, its length runs out of the paper toward the camera, so on the map it is kept at a modest `iconSize` — perspective already enlarges it. `'top'` (lying on the paper, seen from above) and `'side'` (profile) still exist in `IconView` and are the vocabulary for changing one animal's presentation: it is a word in the catalog, not a change to `MarkerPin`. `facing` (degrees of yaw about the icon's own up-axis) is 0 for all four; it is what turns one animal to match its drawing if it ever goes back to profile — keep it. `MarkerPin.stageYaw` gives the focused close-up the same starting face, because the stage does not apply `view`.
  **Calibrate `iconSize` in `/verify.html` by measuring on screen, never analytically.** The on-screen size is *not* `ICON_TARGET_SIZE × iconSize`: `fitToIconSize` normalises the model's largest 3D dimension, and which dimension ends up across the screen versus pointing at the camera depends on `view` and `facing`. Measured drawn widths on the current map, in map widths: whale 0.31, turtle 0.19, guan 0.13, crab 0.08. The targets are a *hierarchy*, not a copy of the drawing — the brief was "no animal too big, the guan not tiny": whale ≈0.25, turtle ≈0.17, guan ≈0.16, crab ≈0.10, which today is `iconSize` whale 2.1, turtle 1.23, guan 1.55, crab 0.95 (whale and crab were raised on request: on the map the whale must read as the biggest animal; the whale's number is not comparable anyway — facing forward, the orthographic view only shows its face and fins). In the focused close-up `iconSize` does nothing — the animal is fitted to the screen — and `focusSize` (≤ 1, per animal) is the knob there: the whale has 0.7, the rest 1. Re-measure with `measureIcons()` after any change to a model, a `view` or the edge rule below.
- **The map-edge clamp (`maxMapScale`) used to be what kept the guan tiny, whatever its `iconSize` said.** It allowed no overhang at all and counted the model's depth as if the user had it turned 90°; the guan stands almost on the right edge of the map and its tail runs backwards, so it was capped at about half size. Now an icon may overhang the paper by `MAP_EDGE_OVERHANG` (it floats in 3D in front of it; nothing breaks) and only its visible width counts. If an animal refuses to grow, compare its `icon.scale` with the others before touching `iconSize`.
- **A translucent panel does not hide what is under it, so the menu moves the hints out of the way instead of covering them.** `#menu` sits above `#approach` by z-index, but at 55% opacity the "Acerca tu cámara a un animal" title read *through* the options. `ArView.syncTransientHints` hides the approach hint and the bottom pill while the menu is open, and `openMenu` retires the guide for the same reason; everything comes back on close. That is why `ArView` keeps `lastSession`: opening a menu changes no domain state, and the hints still have to be recomputed.
- **`MarkerPin` lifts each icon by however much it needs, not by a fixed height.** Facing the camera, a long animal extends *out of the paper* rather than across it, so a fixed `HOVER_HEIGHT` would bury the whale's back half under the map, sliced by the paper plane. `measureHalfDepth` measures the oriented icon once at construction and `sync` flies it at `max(HOVER_HEIGHT, halfDepth × scale + CLEARANCE)`. Flat icons are unaffected; the whale ends up noticeably higher, which is the visible cost of facing forward.
- **MindAR's compiler and its runtime disagree about greyscale, and `scripts/compile-target.mjs` reconciles them.** `CompilerBase` flattens colour with a plain mean `(R+G+B)/3`, but on the phone `input-loader.js` converts each camera frame with Rec.601 luma (`0.299R + 0.587G + 0.114B`) in a shader. Compiled naively, the descriptors in the `.mind` describe an image the camera never produces — a costly mismatch on a map this saturated, where blue counts three times more in the compiler than on the device. The script pre-bakes luma into all three channels before handing pixels to the compiler, so the compiler's mean returns exactly the shader's signal. Measured with `npm run bench-detection`: 8/12 → 9/12 frames detected and 234 → 282 total inliers, at zero runtime cost and identical file size. **Any `.mind` compiled before this fix should be recompiled.**
- **`TARGET_ASPECT` in `src/main.ts` must match the compiled image**, and the catalog's `spot` values are measured against that same image. Changing the map means: re-run `npm run prepare-target` and `npm run compile-target`, update `TARGET_ASPECT` (**1432 / 1000** today), re-measure all four spots, and re-trace all four `outlineShape`s — plus the viewfinder's `aspect-ratio` in `index.html` and the canvases in `verify.html`. They are one unit, not independent settings.
- **The target's pixel width is a tuning knob, and the bench picks it.** Each delivery is compiled at 880, 1000 and 1200 px wide and measured with `npm run bench-detection`. The recoloured map of September 2026: 6/12 hits and 239 inliers, 7/12 and 252, 7/12 and 247 — it ships at **1000×1432**, best on both counts. (The previous delivery, at the same three widths: 8/12 and 289, 8/12 and 308, 7/12 and 305.) Bigger is not better: past a point the compiler stores detail finer than a phone camera resolves at reading distance. **The bench only compares `.mind` files compiled from the SAME `map.jpg`** — it builds its frames from that file, so pointing it at a `.mind` made from a different image reports 0/12 and means nothing.
- **The map arrives as a screenshot of a PDF viewer, and `npm run prepare-target` is what makes it a target.** The delivery has white page margins, a grey viewer shadow down two edges, and whatever pixel size the screenshot happened to have. That grey line is pure contrast at the image border: the compiler reads it as map detail and stores descriptors for something the printed paper does not have. The script crops to the drawing, puts back an even white margin (the print has one, so the compiled image needs one or the catalog's normalized coordinates slide against what the camera sees), and resizes to the benched width. The original stays in the repo root, unserved, exactly like `Pantalla Inicial.jpeg` — never re-run the script over its own output. Ask the designer for the PDF if detection ever needs more: a screenshot caps the detail the compiler has to work with.
- **MindAR always inserts a CSS3D layer over the WebGL canvas, and it eats every tap.** `MindARThree` builds a `CSS3DRenderer` whether or not you use CSS anchors and appends it *after* the canvas (`three.js:42-43`), so its full-screen `<div>` sits on top. three sets `pointerEvents: 'none'` on the inner `viewElement` but **not** on that outer div, and a transparent div swallows pointer events exactly like an opaque one — `document.elementFromPoint()` at the screen centre returned the div, never the canvas, so the raycast never ran and tapping an animal did nothing at all. `MindArRuntime.configureRenderer` now sets `pointerEvents = 'none'` on it. If taps ever go dead again, check that first, not the raycast.
- **MindAR asks iOS for a 640×480 camera, and that alone is most of "it takes a while to recognise the map".** `MindARThree` calls `getUserMedia` with `{facingMode:'environment'}` and nothing else (`three.js:109-125`), Safari hands back its 640×480 default, and that becomes the detector's `inputWidth`, because the `Controller` is built from `video.videoWidth` (`three.js:146-147`). On an illustration this fine, 640 px of frame does not keep enough features and the match takes several attempts to land. Measured on one unchanged `.mind`, varying only the frame width (`BENCH_WIDTH`): 640 px → 7/12 frames and 252 inliers, 960 px → 9/12 and 321, 1280 px → 10/12 and 399. `MindArTrackingAdapter.withSharperCamera` therefore patches `getUserMedia` for the duration of the *synchronous* part of `mindar.start()` — the same crack `silenceVideoChrome` uses — and adds `width/height: {ideal: 1280/720}`. It cannot be done afterwards with `applyConstraints`: by then the Controller exists with the old size and changing resolution skews the projection. `ideal`, never `exact`, so a camera that cannot do 720p still starts.
- **The `.mind` is downloaded during the splash, not after the tap.** MindAR fetches the target inside `start()`, *after* the camera permission (`_startVideo` first, `_startAR` second), so nearly 900 KB used to sit between "Allow" and the first detection attempt. `TrackingPort.prewarm()` is the port method for "get your downloads out of the way before the gesture"; `MindArRuntime.prefetchTarget` fetches the file and keeps it as a `blob:` URL that `init()` passes to MindAR instead of the path. A blob rather than trusting the HTTP cache because Netlify serves these with `must-revalidate`: the cache saves the body, not the round trip. It is best-effort by contract — if it fails, `init()` uses the normal URL and MindAR downloads it as before.
- **In the focused close-up the animal is capped at `STAGE_MAX_WIDTH` of the screen width, perspective included.** The old fit used the silhouette the camera sees at the current spin angle, with the depth weighted at only 0.6 — so a whale facing the camera (length pointing at it) could get up to ~1.3× the screen width in length, and its nose, being nearer, looked bigger still: "bigger than the phone". `updateStage` adds a cap that doesn't depend on the spin angle: the larger of width and length, grown by `d / (d − s·r)` for being nearer the camera. The small animals never reach it, so they are unchanged. `npm test` checks that a long animal stays inside the screen over a full spin. The clients still saw the whale leave the frame, so the close-up was shrunk again (`STAGE_FILL` 0.42 → 0.32 of the height, `STAGE_FILL_WIDTH` 0.76 → 0.6, `STAGE_MAX_WIDTH` 0.82 → 0.62, whale `focusSize` 0.85 → 0.7) and raised by `STAGE_LIFT` (13% of the visible height) into the free space above the card, which used to cover its lower half. **The close-up does not spin by itself** — it had a slow turntable spin (`STAGE_IDLE_SPIN`) and the clients read it as a product in a shop window; it turns only when dragged, and a single tap plays the animation.
- **`FrameLockedBackground` can make the camera background the ANALYSED frame instead of the live video — and it is OFF (`lockBackground: false`), because on an iPhone the image vibrated.** The synced background only refreshes at the tracking rate and freezes on every lost frame, so the natural tremor of a hand showed as an image shaking in steps under perfectly still animals; the brief is "fixed, still and calm". What stays on is the stale-pose watch below (with `MAX_LIVE_MISSES`, a bit more margin, so one lost frame on a still phone never blinks the animals). The history, for whoever is tempted to turn it back on: MindAR shows a live `<video>`, but the pose comes from a frame 50–100 ms old on a mid-range phone, so a sharp move left the animals floating "a destiempo". It is the same fix as ARKit/ARCore: the analysed frame is shown in sync with its pose. MindAR already draws every frame into a canvas (`InputLoader.loadInput`); it is wrapped and copied, GPU to GPU, into one of two canvases that alternate. The cost is visible: while tracking, the background moves at the tracking rate, not the camera's. With no map in view it goes back to live video. **It also fixes stale poses:** after a lost frame MindAR keeps declaring the target "showing" with the last pose for `missTolerance` frames. Now up to `MAX_FROZEN_MISSES` lost frames hold the last good image (animals stay glued to it), and after that the animals are hidden (`isStale` → `runtime.anchorVisible` false) until the map is found again — better a moment without animals than animals in the wrong place. If MindAR's internals are not where they are expected (or the input is rotated) it returns false and the live video stays.
- **The runtime skips rendering when nothing is visible, and has a `lite` profile.** Frame callbacks return whether they left anything to draw; while searching for the map nothing renders, so the GPU — shared with TensorFlow — goes entirely to detection. `lite` renders at 30 fps with pixel ratio ≤ 1 and asks the camera for 960×540 instead of 1280×720 (tracking cost scales with pixels; 960 detects nearly as well, 9/12 vs 10/12). It is chosen up front on phones reporting `navigator.deviceMemory ≤ 4` (Chrome/Android only, which is where the mid-range is), and the governor in `startLoop` drops to it after ~2.5 s of frames slower than ~26 ms — the camera size can't change after start, only render. It never goes back up: oscillating looks worse than either.
- **`warmupTolerance` is 1, not MindAR's default 5.** What costs time is *finding* the map, not confirming it: every warmup frame adds to a wait that is already noticeable, and once a match has inliers the next frame's tracking almost never contradicts it. `missTolerance` stays high (12) — that is the one that stops the content blinking when the marker leaves the frame for an instant.
- **The tap raycast resolves *which* icon was hit**, via a `userData.modelId` set on each pin group and walked up from the hit mesh (`findModelId`). The tap zone uses `opacity: 0` rather than `visible: false` on purpose: three's raycaster still traverses invisible objects, so `visible: false` would not have made it untappable — but it also wouldn't have been reliable across versions.
- **`IconLoader` is the only place a model becomes an `Object3D`**, shared by `ThreeSceneAdapter` and `verify.html` so the verification page tests the real assets. It also owns the two things every incoming `.glb` needs:
  - **Normalization (`fitToIconSize`).** **Map width = 1 unit**, so a `.glb` authored in Blender units or metres is enormous — the delivered models are 9–23 units across. `fitToIconSize` recentres each model on its bounding box and scales its longest side to `ICON_TARGET_SIZE` (0.21, the size `PrimitiveFactory` draws to), so real and procedural icons are interchangeable and no per-model `defaultScale` tuning is needed. It returns a **wrapper** group: `MarkerPin` overwrites `icon.scale`/`icon.rotation` every frame, so the fit factor must live on an inner node or it gets wiped.
  - **Draco.** The models ship `KHR_draco_mesh_compression` in `extensionsRequired`. `public/draco/` holds the decoder copied from `three@0.160.0`; re-copy it if three is ever bumped. `EXT_texture_webp` (also required by these files) needs no setup — three 0.160 supports it natively.
- **The clips are played at the animators' own speed, and that is a rule, not a default.** `tapSpeed` once sped the whale's Jump to 1.8×, the crab's Walk to 2.4×, the turtle's Swin to 2× and the guan's Sing to 1.2×; the animators noticed at once ("the crab feels sped up", "the whale's jump feels cut", "not fluid") and asked for their animations back. All four now play at 1. Anything we add on top (`TapChoreography`, `tameBreach`) is written to the principles they cited — arcs, slow in/out, anticipation, follow-through — and the tests check it has no jerks (no jump in position, pitch or *velocity* between frames). Before speeding up or retiming a clip, ask them. Also: a tap never changes an animal's size (the 30% tap "pulse", the 20% "highlight" of the last one tapped and the turtle's shrink-with-depth were all removed on request), and **a tap during a gesture is ignored** — `MarkerPin.pulse` returns false, `PlayModelSound` then plays no sound either — because re-triggering cut the animation off halfway. When the tap clip is the one already playing (crab walking, turtle swimming), `IconAnimator` continues it from where it is instead of snapping to frame 0.
- **Each animal has an ambient loop and a tap gesture, and they are two layers.** `AnimationSequence.steps` is what it does forever (whale Swin; guan Idle; crab Idle/Walk; turtle Swin/Idle). The tap plays `tapClip` (at `tapSpeed`, 1 for all four), `tapLoops` times, then `IconAnimator` hands the loop back exactly where it was. A tap clip that is also in the loop would make the tap do nothing new — that is why the guan's Sing is tap-only. `tapMove` is catalog vocabulary like `view`: `TapChoreography` moves the *whole animal* on top of the clip (`'leap'`: the turtle swims UNDER the surface; it crouches, rises with ease-in (no jerk at takeoff) and breaks the surface with a small splash, arcs with its nose following the curve, falls in a parabola and splashes harder on re-entry, keeps sinking as the water brakes it and returns to its swimming depth — the splashes are not timed but fired when `rise` crosses the surface height `MarkerPin` passes in, so they always appear where the water is, above the turtle; `'scuttle'`: the crab goes to one side and back in small smooth hops, leaning into the motion). Its duration is the tap clip's own (`clip.duration × tapLoops / tapSpeed`), so body and clip start and end together. The turtle once did `'dive'`: a full spin, sink, then a splash while *surfacing* — water splashing with nothing falling into it, because no delivered clip does that without leaving the map. `MarkerPin.poseIcon` applies it both on the map and in the focused close-up, so the gesture is identical in both.
- **The whale's `Jump` plays at its own 10 s with every rotation intact; `tameBreach` only rescales it and rewrites the hips after the peak.** In the file the hips rise 19 units and travel 20 forward — nearly the whole animal. The rotations tell the story and are untouched: swim (0–1.3 s), nose up and rise (1.3–3 s), roll onto the back at the peak (~3.8 s), nose down (4.4–6.7 s), level out (6.7–10 s). The hips rise keeps its curve, scaled by `BREACH_SCALE` — the same factor for height and travel, so the arc keeps the animator's shape. After the peak: a parabolic fall lasting as long as the rise took (from 10% of the height to the top), so it starts soft and gathers speed; at the water (`impactSeconds`, the splash) it keeps going down with the speed it had, the water brakes it exponentially (same slope on both sides of the impact — no "floor"), and it floats back up with ease in/out. The previous version fell in a quarter of a second what it had climbed in two and a half, stopped dead, and ran at 1.8×: "it looks like it crashes against the floor". `impactSeconds` is returned as `splashAt`, and `MarkerPin` fires the splash when the *clip* crosses it, so a `tapSpeed` never desyncs it. Two earlier attempts failed: measuring the icon's size across the Jump's frames (it shrank the whale to fit a jump it does for two seconds) and adding a hand-made 360° roll on top of the clip's own roll.
- **The whale and the turtle both swim UNDER the water surface, and splash twice: softly breaking out on the way up, hard falling back in.** The surface (`MarkerPin.waterSurface`) is their rest top plus `SUBMERGED_DEPTH`, which is where the splash appears — above the animal. With the splash at the whale's belly, its fall "looked like it hit the floor and splashed"; the turtle's version (splashes above it, out and in) was the one the client liked, and the whale now copies it. The turtle's splashes fire when its choreography's `rise` crosses the surface; the whale's come from `tameBreach` as clip times (`LoadedIcon.splashes`): the rise crosses `BREACH_SURFACE` of the jump height on the animator's curve, and the parabolic fall crosses it again. After re-entry the whale keeps going as deep as it jumped (`BREACH_SINK` 1) and floats back. There was a clipping plane that hid the whale below its belly line while it dived; with the surface above both animals it would hide them while they swim (they are seen through the water, from above), so it was removed along with `renderer.localClippingEnabled`.
- **Every splash has its sound, in the same frame.** `MarkerPin.onSplash(strength)` fires with the visual burst → `ThreeSceneAdapter` → `ScenePort.onSplash` → `PlaySplashSound` → `AnimalSoundscape.splashed`, which plays the catalog's `soundscape.splash` at a volume that follows the splash strength (min 0.3), so the breaking-out splash is quieter than the falling one. The file is the same CC0 "Big Water Splash" for both, whose hit is at 0.0 s: `build-audio` encodes it with a 5 ms fade-in (not the 50 ms of calls, which would soften the hit), and the turtle's version is 1.3 s at `rate` 1.25 — shorter and higher, a smaller body. It is preloaded among the first sounds because it plays at an exact time, and a clip more than 1.5 s late is dropped. That recording used to be one of the whale's *taps*, so it sounded when tapped, before the jump; it was moved out of `taps`. Each mesh re-places it in `onBeforeRender`, when three has already updated that frame's matrices — computed earlier it lags a frame behind a moving phone and the waterline trembles. It works in either parent (map `lift` or close-up `stage`). Needs `renderer.localClippingEnabled = true` (set in `ThreeSceneAdapter.configureRendering` and in `verify.ts`); the plane always exists and is moved far away when idle, because changing the *number* of planes makes three recompile the shader.
- **Skinned meshes are drawn with `frustumCulled = false`.** three keeps a `SkinnedMesh`'s bounding sphere from its rest pose; when a clip moves the body away from it, three decides the mesh is off-screen and skips it — which is why the whale "just disappeared" mid-jump. `IconLoader` turns culling off for every loaded model: four models, nothing measurable saved by culling them.
- **`WaterSplash` reads as water because it falls, is white, and leaves ripples.** The first version was additive-blended flat dots opening in a ring: they glowed and never fell, so they read as confetti. Now droplets launch upward and come back under gravity, stretched along their velocity; a white foam base (normal blending, so it shows on the turquoise map and on a camera image alike); and two squashed rings as the water surface in perspective. It is measured in "animal sizes" and scaled by whoever shows it, so one splash serves the whale (`strength` 1) and the turtle (0.55). Both splash once, on falling INTO the water.
- **three fires ONE `loop` event when a frame wraps several loops, with `loopDelta`.** A short clip at a high `tapSpeed` (the crab's Walk used to run at 2.4) wraps twice in one long frame; counting events instead of `loopDelta` made the tap run longer than `tapLoops`.
- If a `.glb` is missing or fails to load, that model falls back to a grey disc instead of crashing the session — this is intentional, don't add a try/catch that hides the failure differently. A grey disc on screen means *check the console for `[IconLoader]`*, usually a codec the loader wasn't configured for.
- To swap an icon for a different asset: change its `source:` entry in `NUQUI_CATALOG` and drop the file in `public/models/`. Icons are modeled **+Y up** (Three.js's natural orientation); `MarkerPin` rotates the containing group 90° about X so that up becomes "out of the map".
- **`MarkerPin.dispose()` frees textures, not just materials.** `material.dispose()` deliberately leaves textures alone (three treats them as shared), so with textured `.glb`s every `clear()` would leak several MB of GPU memory without the explicit walk.
